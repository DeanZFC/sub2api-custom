# 渠道被动质量保护

入口统一在「渠道质量管理」的「实时流量保护」和「事件与恢复」。新建策略使用 schema_version: 2，默认仅观察、scope=model（模型隔离）；缓存和首字指标仍需管理员按需启用。没有新增默认生效的生产保护策略。
本次模型隔离仅适用于实时流量保护；定时主动检测的配置、判定和处置范围保持原有语义。

## V2：按指标独立判定和恢复

| 指标 | 可选处置 | 恢复证据 |
| --- | --- | --- |
| 可用率 / 连续失败 | 暂停调度或限制并发、降权 | 暂停经冷却、单次探测、限量真实流量验证；限流使用新的可用率样本 |
| 首字 P90 | 仅观察或独立限制并发、降权 | 新的有效首字样本连续达到更健康的阈值 |
| 缓存复用质量 | 仅观察或减少新会话分配 | 新的可复用请求达到恢复阈值、独立会话要求和保持时间后分步增加分配 |

可用率仍使用策略顶层动作、窗口和冷却/试运行预算，各模型隔离状态分别使用这些配置；首字使用独立 ttft_action、ttft_concurrency_limit、ttft_priority_penalty。缓存配置和状态完全独立。缓存样本不足不会阻止可用率恢复；一个指标恢复不会清除另一指标、其他策略或人工停用的限制。硬错误、余额/配额、429 冷却和协议归属等原有准入约束继续优先。

V2 默认按账号 + 实际请求模型分别统计可用率、首字和缓存，模型筛选留空表示“全部模型分别评估”，并非混合账号窗口。单个模型异常只限制该模型，其他模型继续服务；每个模型拥有自己的确认、冷却、探测和试运行恢复预算。指定模型筛选时只处理该模型。管理员可显式选择 scope=account 继续采用整账号处置，此时模型筛选只限定证据来源，账号动作可能影响所有模型；缓存依然按模型积累复用证据，混合首字阈值需要校准。缓存只改变新会话分配，不设置缓存专用的并发上限，不因缓存率低暂停整个账号。

## 两种缓存率

- **实际缓存使用率**：全部明确报告缓存计数的有效请求，缓存读取 tokens 总和 / 有效文本输入 tokens 总和。反映成本和利用率；包含冷启动、切号后的缓存重建，不用于直接处罚账号。
- **保护缓存率**：仅使用发送前可识别复用机会的请求，已读取的可复用 tokens / 预期可复用输入 tokens。明确报告零命中仍作为有效异常证据；不能把所有零命中都解释为冷启动。
- **未知不等于零**：未报告缓存用量、无法确认上游缓存范围、会话或前缀不可见、采集有缺口时，显示未知或证据不足。预热到期且没有有效复用证据也不会显示恢复。

复用识别综合租户/会话摘要、实际账号、模型、上游缓存作用域、稳定前缀摘要和完成时间。元数据必须来自实际发往上游的最终请求并通过 wire_verified 校验，不能仅依据入站请求猜测；仅已知实际上游缓存作用域的直连请求可进入复用判定。此前的相同或可扩展前缀请求必须在当前请求开始前已经完成，且仍在配置复用间隔与当前/前次请求供应商保留期限的较短边界内。有效期保守地从前次实际出站时间计算，长响应完成不会重新延长缓存寿命；当前响应是否命中不参与复用机会分类。首次落到账号、账号切换、前缀改变或复用过期分别显示冷启动/预热或未知原因。

只保存必要摘要与元数据，不保存请求正文或上游凭据；现有 usage_logs.session_id 保持原本的客户端关联标识语义。服务端隐藏历史、未知缓存边界、未经验证的中转作用域、外部/多模态内容及未支持的协议/请求形态保守标记未知，不根据用户身份或会话标签直接推断可复用。

## 快速感知与保守减量

| 配置 | 快速观察 | 自动减量 / 恢复 |
| --- | ---: | ---: |
| 最多回看 | 300 秒 | 900 秒 |
| 最近请求上限 | 50 | 200 |
| 最少可复用样本 | 15 | 30 |
| 连续异常确认 | 2 | 3 |
| 每次新增可复用样本 | 3 | 5 |
| 最少可复用输入 tokens | 32768 | 65536 |
| 最少独立会话 | 3 | 3 |
| 单会话最大 tokens 占比 | 60% | 60% |

时间和数量限制同时生效，并非固定每 5 分钟平均 15 条请求。后台约每 15 秒评估一次，达到样本、tokens、会话和集中度要求才判定；同一批样本不会重复增加确认次数。快速窗口只产生观察提示，自动减量使用更保守的独立窗口。通用灵敏度模板只改变可用率/首字窗口，不隐式覆盖缓存窗口。

自动减量窗口的时间、样本、tokens、会话和确认要求不得低于快速窗口。每个独立会话至少贡献 2 条有效复用证据；单个大会话即使贡献大量 tokens，也不能单独触发账号级缓存减量，异常还须有多个会话支持。不同会话出现混合结果时保留观察，而不是声称整个账号健康。

## 保留会话、渐进恢复与防连锁

默认缓存异常时保留 **25% 的新会话分配机会**，健康的既有会话继续命中原账号。它是新会话候选分配比例，不是账号并发比例或总请求比例，也不是对每个有限样本窗口的精确流量承诺；抽样排除的候选仍保留为兜底层；首选层无账号、实时复核失效或无法取得并发槽时，再对兜底层执行原有硬性准入检查，以保留可用容量。硬故障需要切换时，新账号重新积累预热证据；缓存恢复不强制会话迁回，避免反复切号重建缓存。

默认减量最少保持 300 秒。恢复要求连续 2 次新可复用证据达到更健康阈值，且独立会话健康；每步增加 25 个百分点、步骤至少间隔 300 秒。无流量、重复样本、只有新会话的冷启动或未知遥测不会视为恢复，也不会把缓存减量升级为暂停。保留真实会话和少量新分配，用真实请求验证恢复，不新增缓存专用付费探测。

账号池默认最多同时对 50% 的账号执行缓存减量，并至少保留 1 个正常分配账号。因账号级模型限制影响共享该账号的所有分组，容量检查覆盖账号所属的全部有效分组，并取重叠策略中更严格的上限；不会只检查当前策略选择的分组。达到边界时停止扩大缓存减量，显示账号池防连锁和共同原因提示；真正不可用的账号不会因池容量要求被强制放开。多个策略分别管理限制，恢复或豁免不会清除其他来源。多实例执行与状态合并复用数据库锁、版本/世代校验与已有准入机制。

## 后台证据与历史回放

保护记录按策略 + 账号 + 实际模型分别展示状态，手动验证、豁免及结束豁免携带具体模型，不能通过省略模型扩大到账号范围。快速和减量窗口分别展示实际/保护缓存率、总样本、可复用、冷启动、未知、缺遥测样本、tokens、独立会话、最大会话占比、异常/健康会话数、确认进度、新会话分配比例、保持时间及原因。两个缓存窗口另显示成功相关请求的切号次数、首字 P90（及有效条数）和输入与缓存计价费用（及记录覆盖条数）。费用为用量记录中未缓存文本输入、缓存写入和缓存读取费用之和，按系统记录费率计价，不是供应商账单或最终扣费，也不提供估算节省；已记录零费用不证明费率完整。成功率与失败归因使用独立可用率证据，不能从缓存窗口推断。首字和可用率状态独立显示，账号池守卫原因可直接定位。

状态和事件均先在服务端筛选再按游标分页，接口默认每页 100 条、最多 200 条；分组目标卡片的状态列表每页 20 条。状态支持策略、账号、模型、阶段，事件支持策略、账号、模型、类型和起止时间。全局及每策略汇总独立于分页，不能用当前页行数推断完整保护数量；加载更多后保留已展开列表，筛选或策略版本变化时重新加载首屏，丢弃旧请求结果。

历史回放使用同一复用分类、汇总和状态推进语义；模型隔离草稿按实际模型输出独立判定点，不把不同模型的样本或确认混在一起。旧历史没有发送前的复用元数据时明确提示“缓存保护不可回放”，不回填零、不凭历史正命中反推复用资格。回放不发送上游请求，也不能模拟限制实施后真实用户切号、上游缓存保留时间或实际节省成本；回放也不模拟限制后的账号池容量，局部预计减量可能被线上防连锁守卫阻止。调参需同时观察切号、成功率、首字和输入成本。

## 旧策略升级

没有 schema_version: 2 的策略继续使用下面的旧版联合判定，不静默改变生产处置。列表与编辑器显示“旧版联合判定”；普通编辑、启停和应用灵敏度模板不会自动升级，也不将已有显式账号范围悄悄改为模型范围。

管理员明确点击“升级为独立保护”才生成 V2 草稿：保留分组、模型筛选、阈值与通用预算，默认切换为模型隔离，加入独立缓存配置，并切回仅观察。保存前明确提示会清除当前策略的保护状态并重新积累证据；其他策略不受影响。新模式验证后可单独开启自动保护。代码更新、迁移成功和生产策略切换是不同步骤。

## 旧版策略语义（schema_version 0 / 1）

入口为「渠道质量管理」的「被动保护」与「保护记录」。检测策略和检测类型保持独立。新建策略默认仅观察，启用自动保护需要明确选择处理方式；没有默认启用的生产策略。

### 旧版判定口径

- 模型筛选可留空，默认按所选同平台分组内的每个账号汇总全部模型的真实请求，并对整个账号应用保护；可排除账号。填写模型时只统计该请求模型，处置范围可选当前模型或整个账号。已有指定模型策略保持原来的筛选和处置范围。
- 混合模型下，错误率、连续失败统一统计；首字和缓存仍只使用各自有效样本。不同模型速度和缓存能力有差异，建议先观察或历史回放校准，再启用首字、缓存保护。
- 同时限制最近请求数量和回看时间。每次连续确认必须有配置数量的新样本；无请求不能证明健康。
- 错误率包含该账号的上游失败，即使随后切换账号完成请求。单个账号同一 HTTP 请求的重试错误去重；WebSocket 按 turn 记录。
- 401、402、429、上游 5xx 和网络请求错误属于质量失败。客户端参数错误、内容拒绝、取消、网关本地并发不足不作为上游质量失败。
- OpenAI Responses（包括原样透传）及 Chat Completions 的客户端断开不会抹去已经确认的上游 HTTP 故障：即使最终请求显示 499，实际收到的上游 401、402、429 或 5xx 仍计入对应账号的失败。纯取消产生的网络错误或网关兜底状态不作为上游故障；账号最近请求的最终状态与上游尝试状态应分别查看。
- 首字采用流式请求有效首字时间的 P90。缓存使用率是缓存读取 tokens /（未缓存文本输入 + 缓存写入 + 缓存读取 tokens），排除图片输入、缓存管理和压缩请求。
- 缓存计数缺失和明确报告 0 不等价。仅已知正缓存读取量或明确报告缓存计数的请求参与缓存判定。未识别上报格式的协议会显示缓存样本不足，不推断为 0。
- 每个启用指标都需要各自的最低有效样本。任一指标达到异常阈值可以触发；恢复必须所有启用指标达到更健康的恢复阈值。

### 旧版恢复流程

可选择“暂停调度”或“限流降权”。限流会降低匹配请求的并发上限与候选优先级，继续观察真实请求；连续达到恢复阈值后解除，不发起主动探测。详见 [整体质量管理](channel-quality.md)。以下为暂停处置流程。

`暂停 → 冷却 → 单次账号探测 → 限量真实请求试运行 → 恢复`

全部模型策略从触发窗口中自动选择探测模型：优先最近失败请求的模型，没有失败则使用最近请求模型。所选模型会保留至冷却和无流量试运行之后，界面可查看；无可用模型时保持暂停并暂缓探测，不盲用平台默认模型。指定模型策略继续探测所指定的模型。

探测只验证可调用性，不证明缓存率、错误率或真实负载下的首字恢复。试运行仅统计开始后的新请求，且有独立的请求数、并发数、时长和样本下限。样本不足超时仍暂停。再次失败后指数退避并加入小幅抖动，冷却时间不超过配置上限。

全部模型策略的试运行请求数与并发额度由账号下所有模型共享，恢复指标也按账号汇总。指定模型策略只使用该模型的流量恢复；与全部模型策略重叠时，该限制仍有效。无模型信息的请求不会消耗试运行额度或绕过保护。

试运行用 PostgreSQL 行锁和请求租约在多实例之间共享额度。只有每个适用保护都批准，才允许调度；其他准入门拒绝时会退还尚未实际使用的被动试运行额度。请求异常退出、租约无法清除时不凭时间猜测请求已经结束，当前试运行最终会超时重新冷却。

付费恢复探测共用[每日检测预算](channel-quality.md#检测预算与动态频率)，可在全局和每账号上限内预留恢复份额；普通检测不能耗尽未使用的预留，恢复也不能绕过两级总额准入。该日预算与真实请求试运行的次数、并发和时长限制分别计算。

保护与账号人工状态、主动检测、限流、额度相互独立，不直接修改 `status` 或 `schedulable`。快照保存保护摘要用于预筛选，真实准入再次查询数据库。账号移出目标分组、策略行为变更或删除会清理本策略的状态；版本和世代校验防止旧探测重新放行。仅改名或原样保存保留已有保护与证据。

## 通用管理与运行

- 「立即验证」提前安排探测，不直接解除暂停；其他人工或主动限制仍会阻止试运行。
- 「临时豁免」为选中的策略状态设置 1 分钟至 24 小时的豁免；V2 模型范围仅豁免当前账号的指定模型，账号范围仍按账号豁免，到期后重新积累样本。
- 原样保存不增加策略版本；仅改名保留证据起点、确认进度、冷却、试运行及现有限制，只更新名称。分组或排除账号列表仅调整顺序也不重置。修改阈值、范围、启停或其他保护行为才清理本策略旧状态并重新积累证据；其他策略不受影响。
- 后台每 15 秒尝试评估，通过数据库锁选取执行实例；每个策略每轮最多处理 128 个最久未评估目标，策略和目标均轮转，避免大批目标下长期饥饿。全局最多同时安排 4 个有效探测。
- 失败采集独立于可关闭的运维日志，不记录请求正文、凭据或错误响应内容。异步队列有上限，批量落库失败会保留待写记录与缺口并重试；本实例未排空采集积压时跳过该轮评估。缺口按时间区间、账号、分组、模型和采集类型记录，仅影响匹配窗口；未知范围或旧版全局缺口保守扩大影响，受影响指标的证据不能用于判定或恢复。
- 成功用量沿用现有 usage_logs；新请求边界用完成时间减请求耗时保守估计。指标受异步用量落库延迟影响，因此这不是逐请求同步拦截器。
- 采集诊断展示当前服务进程的队列深度、待写/丢弃数、待写缺口、积压时长、最近落库/评估/清理时间和错误，以及因积压跳过的评估次数；这些计数不是集群汇总，也不替代各策略的证据完整性判断。页面可见时每 15 秒刷新。
- 失败及缓存上报标记保留 2 天，保护事件保留 30 天；清理独立于策略评估，按批次执行。
- 迁移 `291_passive_quality.sql` 新建独立表，复用既有用量索引；`295_passive_quality_account_window.sql` 为全部模型的失败窗口补充账号与时间索引。发布升级后由现有迁移框架执行；不需要修改已有主动检测策略。

- 迁移 301_passive_quality_reuse_evidence.sql 为缓存上报标记增加请求时的摘要元数据和有界复用查询索引；不改写旧策略、不补造历史复用证据。升级后需积累新流量才能判定 V2 缓存保护。
- 迁移 303_passive_quality_model_states.sql 为保护状态和试运行租约增加模型维度，已有 V2 指定模型状态保留对应模型；旧版和账号范围策略保持账号身份，不自动切换保护范围。

## 验证

后端单元测试覆盖阈值、缺失数据、上报零值、去重标识、模型准入、退避、主动保护拒绝时的额度退还和管理 API 校验。PostgreSQL 集成测试覆盖连续确认、观察模式、错误归因、跨连接并发预算、冷却与试运行、超时、人工停用、账号移组、策略版本冲突、旧探测结果和租约退还。前端测试覆盖策略保存、无效恢复预算、状态证据、立即验证、豁免和错误重试。


V2 增加冷启动、账号切换、复用过期、明确零命中、未知遥测、多会话集中度、新样本确认、分步恢复、池守卫及旧策略兼容测试。后台界面测试另覆盖显式升级回到观察、旧策略普通编辑不升级、缓存参数约束、独立证据与未知展示、复合回放动作和总览的缓存减量标签。回放不替代上线后对真实切号和成本的观察。

## 分组质量目标（实际请求）

渠道质量管理 → 自动保护 → 分组质量目标提供简化配置：选择分组，设置缓存率、可用率和首字 P90，再启用保护。新建 GPT-Pro 预设为缓存率 >80%、可用率 >80%、首字 P90 <15 秒；GPT-Plus 预设为 >70%、>70%、<20 秒；已有策略阈值保持不变。每个指标可以单独关闭。能力检测入口继续使用已有主动计划，支持鹈鹕生成与人工评审、总耗时、糖果答案和模型一致性。

该功能使用 `purpose=group_quality_target` 的独立策略，按分组内实际出现的每个模型分别维护账号状态，采用实际上报的文本缓存 token 比率，不要求上游具有已证明的可复用缓存作用域。它不会修改旧 V2 可复用机会的判断，也不会把缺失计数伪造成缓存命中。缓存率按 token 加权，明确上报的零命中也是有效样本；图片 token、压缩请求和非文本生成请求不用于缓存目标。首字使用流式/WS 请求的 P90；可用率统计该分组完成的上游请求尝试，失败优先于同一次尝试的部分用量，不能与最终用户请求成功率混用。

默认每个账号模型回看 1 小时/最多 100 条，至少 5 条有效指标样本，连续两次确认且每次增加至少 2 条对应指标样本后暂停。缓存率/可用率等于下限、首字等于上限均视为未达标。冷却后只开放限量真实流量试运行（默认并发 1、最多 20 次、15 分钟），各项启用指标均有足够新样本并超过恢复门槛后才恢复；连接探测成功不能代替真实达标。缓存/可用率恢复门槛默认比目标高 5 个百分点，首字恢复门槛为上限的 80%。失败再次冷却，手动停用和其他检测的暂停仍独立有效。

首次异常由完整窗口建立待确认状态，后续确认要求同一指标的新增样本本身也达到异常阈值；旧异常仍在窗口内、但新到样本健康时不会继续累计确认。切换异常指标或证据过期会重置确认，未知指标不按零处理。页面分别显示完整窗口与新增证据的指标值和有效样本数；这项新增异常确认规则仅适用于分组质量目标。

卡片上的最近 1 小时指标来自后台定期生成的真实请求报告，与暂停时保留的判定证据分开。报告正常约每分钟更新，显示窗口和生成时间；首个快照未生成或超过两分钟未更新时不判为当前达标。分组指标、流量统计与账号/模型/用途贡献明细来自同一次数据库快照，明细最多展示 200 条并提示截断；无法关联请求用途时显示未归因。没有样本、缓存计数缺失、故障采集缺口，或升级前无法归属分组的失败记录，都不能证明达标；页面显示待样本/未知。原有低质量请求不会被清空，历史滚动指标需要随真实流量变化。

这是质量筛选与自动恢复目标，不是对未来请求的数学保证。冷启动、新模型、低样本、上游变化和限量恢复流量可能暂时拉低分组统计。如果所有账号均不合格，保护状态与缺少已验证供给的提示仍保留；OpenAI 分组可按[全组评分兜底](channel-quality.md#全组按评分兜底)为单次请求取得许可，仍须通过人工状态及其他硬性准入，不代表账号已恢复达标。暂停门目前按账号+模型生效；跨组共用账号会同时受到影响，其他组流量也可能消耗该账号模型的试运行预算。需要不同服务等级时，优先使用独立账号池。

升级迁移 305 为失败证据新增 `group_id` 与索引；旧记录保留 0（未知），不猜测归属。迁移是增量兼容的；升级前仍应备份生产数据库。
