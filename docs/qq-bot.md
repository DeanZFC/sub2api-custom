# CTAV QQ 群机器人接入说明

管理后台入口：「QQ 机器人」一级菜单，下设基础配置、账号绑定管理、活动记录、活动配置四个二级菜单。「活动配置」包含签到配置、抽奖活动、邀请奖励三个 Tab，各自独立保存；切换 Tab 会保留当前页面尚未保存的内容。旧地址 `/admin/qqbot` 自动跳转至 `/admin/qqbot/config`。用户绑定入口：「个人资料」。运行在现有 Sub2API 服务中，使用 PostgreSQL 保存任务和奖励记录。部署后需在 QQ 开放平台配置回调，并填写中转站的模型与凭据。

## 已实现的功能

- 全员免费文字聊天：使用站长配置的 Base URL、API Key、聊天模型；支持 Chat Completions 和 Responses。
- 文生图：可复用聊天连接，也可配置独立生图连接；将生成图片直接发送到 QQ 群。
- 每个机器人、每个群独立的共享聊天上下文，区分成员身份和昵称；历史条数可配置，连续 30 分钟无聊天后重置。
- 可选群聊自主回复：直接呼叫昵称、择机接话和一次短窗口续聊，按群独立限额、静默失败，默认关闭。
- 网站账号绑定：群内发送注册邮箱，收到邮件后打开确认页完成绑定，无需登录网站；也保留网站生成绑定码、群内发送后回网站确认的方式。
- 每日签到：独立开关，支持指定最低和最高金额随机发放，以及累计/近 N 天充值门槛；按北京时间每天一次，多个群也不能给同一网站账户重复发放。
- 群内抽奖：配置余额奖项与概率，累计充值赠送次数，历史在线余额充值与余额兑换码额度也计入；可设置累计每 N 次使用独立保底奖池，支持用户次数查询、保底进度和管理员分页查询抽奖记录。
- 邀请奖励：依据 QQ 官方邀请申请和成功入群事件，双方绑定后发放给邀请人；退群重进不重复奖励。
- 奖励入账、流水与余额历史使用同一数据库事务，赠送不触发充值返利。
- 群白名单、每人和全站每日聊天/生图次数、请求冷却、奖励上限，以及任务与奖励记录。
- 管理员可查看、搜索和分页浏览已绑定账号，并解除绑定；解绑操作记录管理员审计日志。
- QQ 回调验签、重复消息去重、持久化任务队列、跨实例并发限制。未知结果的模型调用不会自动重试。
- 渠道价格、分组倍率、启停和删除自动群通知，可同时通知高峰和优惠时段切换；通知无需调用 AI。
- 模型价格与个人今日用量查询、连续签到和成长任务抽奖次数奖励，以及基于被动监控的故障/恢复通知。

支持图片理解、群共享聊天上下文和引用机器人消息时的上下文识别；图片编辑、语音对话不包含在当前版本中。

## 费用与默认限制

聊天和生图只使用站长配置的 API Key，不使用群成员的 Key，不扣群成员余额。签到、邀请和抽奖奖励增加的是成员在网站上的余额。

默认：机器人和生图开关关闭，奖励金额为 0；每人每天 30 次聊天、2 次生图，全站每天 500 次聊天、20 次生图，冷却 5 秒。次数设置为 0 表示禁用，不表示不限量。模型调用失败或超时仍占用一次次数，因为上游可能已经计费。

建议为机器人建立独立的站长 API Key，在中转站设置该 Key 的金额预算。机器人限制的是调用次数，不能从任意中转站的 Token 数准确推断实际账单。后台「测试聊天」「测试生图」会真实调用上游，可能产生费用；管理员测试不占群用户每日次数。

## 部署后配置

1. 使用包含本次修改的前后端构建部署。新增 SQL 迁移会由项目现有迁移机制执行。
2. 服务器必须设置固定的 `TOTP_ENCRYPTION_KEY` 才能保存 AppSecret 和 API Key。若已经有这个配置，沿用原值，不要更换。它用于加密保存凭据，后台读取时不会返回密钥原文。
3. 打开「管理后台 → QQ 机器人 → 基础配置」，先保持总开关关闭，填写 QQ 的 AppID、AppSecret、是否使用沙箱，保存。
4. 在 QQ 开放平台配置 HTTPS 回调地址：`https://你的站点域名/api/v1/qqbot/webhook`。不要使用本地预览的 localhost 地址。
5. 接入 `GROUP_AT_MESSAGE_CREATE` 和 `GROUP_MESSAGE_CREATE`，由群主在最新版手机 QQ 中打开群内机器人的权限设置，开启“接收所有消息”。后者是无需 @ 执行指令的前提；全量模式识别机器人本人的 @ 还需 `/v2/groups/{group_openid}/bot_state` 接口权限。帮助菜单的直接执行和翻页按钮还需订阅 `INTERACTION_CREATE`（`INTERACTION`，`1<<26`），并具备互动回应接口权限。邀请奖励还需要 `GROUP_JOIN_REQUEST`、`GROUP_MEMBER_ADD`、`GROUP_MEMBER_REMOVE`。平台事件权限以你的机器人实际权限为准；申请事件要求机器人是群管理员。
6. 将 CTAV 加入测试群，触发一次加群或 @ 消息事件。在后台点击刷新，将发现的群 OpenID 加入允许列表。OpenID 与普通 QQ 群号不同。
   自动识别列表支持逐条删除，删除后立即生效，仅清除当前机器人的群发现记录，不改动允许群配置、账号绑定和活动记录；后续收到该群的新事件时会再次识别。
7. 填写中转站 API 根地址（通常为 `https://你的中转站/v1`）、机器人专用 API Key 和聊天模型。不要把 `/chat/completions`、`/responses` 或 `/images/generations` 填入 Base URL。
8. 若需要生图，填写实际支持 `/images/generations` 的模型并打开生图开关。独立生图地址必须同时配置独立生图 Key，以免将聊天凭据发往另一个服务。
9. 保存后分别测试 QQ 凭据、聊天和生图。QQ 凭据测试成功只代表可获取调用凭证，仍需测试群验证消息和事件权限。
10. 在「QQ 机器人 → 活动配置」设置签到、抽奖和邀请奖励规则，再到基础配置启用机器人。使用正式环境时按 QQ 平台要求配置服务器出口 IP 白名单。

## 模型价格与今日用量

- `/价格 模型名`：不调用模型，按完整模型名查本地当前计费规则。未绑定时展示非专属分组公开报价；已绑定时按账号可绑定的分组及个人专属倍率计算本人报价。订阅分组的报价不代表已获得使用资格，仍需有效订阅。价格、分组名称和本人报价都会发到当前群。
- 查询沿用 Group → Channel → 默认价卡解析和实际计费函数，包含当前分组/用户倍率、分组高峰倍率、渠道分时倍率、DeepSeek 默认峰谷价、已启用的上下文阶梯；标准服务层级、默认推理等级，金额单位 USD / 百万 Token 或 USD / 次。缓存写入展示默认时长，图片/音频和工具调用等额外项目不包含在文字 Token 报价中。
- 已配置的渠道映射按计费来源选择模型；按最终上游或响应模型计费时，明确标注请求模型参考价。报价不探测账号可用性，也不代表所有账号都支持该模型。未知且无明确价卡的模型不使用模糊兜底猜价。
- 长结果按完整档位分段，每次最多 5 条；`/价格 模型名 2` 查看下一页。每页重新查询当前价格。
- `/今日用量`：须绑定有效网站账号，只能查看本人。从北京时间当天 00:00 到查询时刻统计已入库使用记录，显示请求数、输入/输出/缓存 Token、实际计费、余额扣费、套餐消耗，以及按费用排序的前 5 个模型。未结束、未入库及已清理的记录不计入；不把套餐消耗误称为钱包扣款。群内结果不含邮箱、API Key 或请求内容。

## 连续签到与成长任务

在「QQ 机器人 → 活动配置 → 签到配置 → 连续签到与成长任务」设置奖励次数，各项 **0 表示关闭**，范围 0～1000；升级默认全部关闭。

- 连续签到每满 **7 天**自动奖励抽奖次数（第 7、14、21 天等），缺签后从头累计。日期按北京时间，历史签到记录参与计算；不追补开启前错过的连签奖励。签到余额、签到记录和连签抽奖次数在同一事务提交，失败全部回滚。签到金额为 0 也计一天，原有充值门槛继续生效。
- `/成长任务` 显示当前连签、累计签到与任务状态；查询不领取奖励。`/领取任务 1` 领取完成账号绑定奖励，`/领取任务 2` 领取首次成功 API 使用记录奖励，`/领取任务 3` 领取累计签到 30 天奖励。
- 三项成长任务独立配置，每项每个网站账号终身限领一次，换群、重启、解绑重绑不重置。历史已有绑定、使用和签到记录也可完成任务；首次调用依据已入库的使用记录，不额外调用模型验证。尚未绑定、账号停用或任务关闭时不能领取。
- 新增奖励直接写入现有抽奖次数账本，`/抽奖次数` 可查并使用；抽奖活动需另行开启。成长任务和连签不增加余额、不计有效充值、不触发充值赠送或返利。

签到回复示例：

```text
✅ 签到成功
到账额度：USD 0.10
连续签到：7 天
连签奖励：2 次抽奖机会
距离下次连签奖励：7 天
```

## 故障与恢复通知

在「QQ 机器人 → 基础配置 → 价格与状态通知 → 故障与恢复通知」单独开启，默认关闭。接收群留空表示所有允许群。需要 V2 被动监控及 QQ 主动群消息权限，不依赖最近群消息，不调用 AI、不发起付费测试请求。

每 30 秒读取最近 **5 个完整分钟**的被动监控聚合，复用监控配置的分组、平台及忽略错误规则，按平台与分组分别判断。默认最少 **50 次请求**，错误率 **≥20%** 或首 Token P50 **≥10 秒**，连续满足 **3 分钟**后通知故障。同一故障只通知一次；错误率 **≤5%** 且首 Token P50 **<8 秒**连续 **2 分钟**后通知恢复。首 Token 阈值设为 0 可只按错误率判断。所有阈值与确认时间都可配置。

再次故障通知默认冷却 **30 分钟**（从上次故障通知入队计时），恢复通知不受冷却限制。无请求、样本不足、数据超过 2 分钟未更新、历史回填或覆盖不完整时，不推断故障或恢复；观察中断超过 90 秒会重新累计确认时长。监控自身不可用不会被当成全部渠道恢复。

状态持久化，多实例通过数据库锁去重；状态变化和全部接收群通知入队在同一事务完成。与价格通知共用每机器人至少 3.1 秒的串行发送限制。积压超过一小时丢弃，发送失败或结果不明不自动重发，后台通知记录保留原因。关闭、变更阈值/接收群/QQ 环境会取消排队通知并重新观察；已开始发送的消息无法撤回。迁移 `286_qq_bot_health_notifications.sql` 新建状态表和队列索引。

## 价格与状态通知

在「QQ 机器人 → 基础配置 → 价格与状态通知」开启自动通知；默认关闭。「同时通知定时进入和退出高峰 / 优惠时段」默认勾选。接收群留空表示所有允许群，也可填写允许群列表中的部分 OpenID。

通知覆盖所有启用渠道的模型价格（包括 Token、缓存、图片、按次和区间价格）、Fast / Flex / 思考强度倍率，以及所有启用分组（含专属、订阅分组）的倍率、图片倍率、视频倍率和高峰规则。渠道和分组的启用、停用、删除也会通知，与定时通知开关独立。只播报变动项，不包含账号统计成本或用户专属倍率。新增渠道 / 分组、首次开启通知及修改通知设置时建立当前基线；停用期间的价格修改只记录现状，重新启用仅通知状态变化。已有渠道新增或移除模型定价会通知。仅更改名称、描述或保存相同价格不会通知。

后台修改通常在 **15 秒内**被检测，同一检测间隔内的修改合并为前后差异。定时通知复用实际计费函数：渠道分时规则按各自配置的时区、工作日和秒级时段边界判断；订阅分组高峰规则按服务端系统时区判断。进入与退出时段都会通知。服务停机或数据库不可用期间不会追补每一次时段切换，恢复后比较最新状态。

示例（同一条通知只列出改变的项目）：

```text
渠道：示例渠道
模型：示例模型（openai）
输入：USD 2 → USD 1.5 / 百万 Token

分组：示例订阅组（定时切换）
倍率：1× → 0.8×

分组：示例分组
状态：启用 → 停用

分组：示例分组
已删除
```

主动通知使用 QQ Markdown 群消息，不依赖用户最近发言、不 @ 用户，也不调用模型或占用聊天次数。需要机器人具备 QQ 主动群消息权限。后台同一区域可查看最近 50 条机器人任务中的通知状态和失败原因；修改价格不会等待 QQ 发送结果。发送按机器人串行限速，至少间隔 3.1 秒，批量消息按顺序排队；积压超过 1 小时的通知标记过期。多实例通过数据库锁和持久化基线防止重复入队，基线更新与通知入队在同一事务完成。QQ 返回失败、发送超时或进程中断时不自动重发，避免无法确认结果的消息重复到群。

迁移 `283_qq_bot_price_notifications.sql` 创建基线表和队列索引。关闭通知、变更接收群或切换 QQ 沙箱环境会取消尚未开始发送的通知；已经发出的请求无法撤回。参考：[QQ 发送群聊消息与主动消息频控](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_messages.post.html)。

## 群内指令

功能指令必须以 `/` 开头。帮助、渠道状态、绑定、签到、额度和奖励查询、抽奖、活动查询及生图无需 @ 机器人；普通聊天默认需要 @ 机器人，或引用本机器人在当前群内最近 24 小时发送的消息；开启「群聊自主回复」的指定群可直接呼叫昵称或由机器人择机接话。无需 @ 的指令和明确聊天回复会在开头 @ 发起人，自主接话默认不额外 @；@ 机器人触发的被动回复沿用 QQ 自动添加的 @，避免重复提及。`/帮助` 返回带标题、指令说明和可点击按钮的分页菜单，自定义指令追加到后续页。未开启自主回复时，普通群消息仅进入有界共享历史，不触发模型或消耗聊天次数；未 @ 的未知指令忽略，@ 后的未知指令仅返回帮助提示，不调用模型。

所有群内文本回复（含直接发送指令、@ 机器人、引用追问、自定义回复、处理中和错误提示）统一通过 Markdown 消息（`msg_type=2`，`markdown.content`）发送正文；全量群消息的指令/明确聊天回复在正文前添加 `<qqbot-at-user id="member_openid" />`，且不同时传顶层 `content`。纯文本消息（`msg_type=0`）实测会将 @ 标签原样显示，仅替换标签不能解决；旧的 `<@openid>` 也不再使用。正文按 QQ Markdown 格式渲染，结构化查询使用标题、列表和留白；普通文字中的 HTML `<br>`/`<br />` 统一转换为换行，代码示例中的标签保留。内置活动与额度回复的美元金额统一显示为 `USD 19.00`，避免连续 `$` 与客户端公式语法冲突；模型公式和代码不会被统一替换货币符号。@ 机器人触发的回复继续使用 QQ 自动提及，图片继续使用独立富媒体消息。Markdown 发送失败时保留错误，不退回携带标签的纯文本。协议依据：[QQ 文本交互](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/trans/text-chain.html)、[发送群聊消息](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_messages.post.html)、[Markdown 消息](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/type/markdown.html)。QQ 客户端的实际 @ 展示仍需部署后在群内验收。

只 @ 机器人而不输入其他内容（包含仅有空白字符）时，直接返回与 `/帮助` 相同的帮助首页，不调用模型。

### 可点击帮助菜单

`/帮助`、`/help` 和只 @ 机器人均打开帮助首页。每页最多 8 个功能按钮（两列），底部仅提供翻页按钮：第一页显示「下一页」，中间页显示「上一页」和「下一页」，最后一页显示「上一页」；也可手动发送 `/帮助 2`。首页提供每日签到、我的余额、我的奖励、渠道状态、抽奖一次、抽奖次数、邀请奖励、我的邀请；抽奖活动、绑定、奖励兑换、生图、转账和启用的自定义指令位于后续页。

- **直接执行**：蓝色按钮通过 QQ 的 `action.type=1` 回调执行对应功能或翻页，不要求用户再发送指令。任何群成员都可以点击，使用点击者的 QQ 身份查询、签到或抽奖；点击「抽奖一次」会消耗点击者的一次抽奖次数，仍受原有活动规则约束。
- **填写参数**：绑定、奖励兑换、生图和转账使用灰色 `action.type=2` 指令按钮，把指令前缀填入输入框；用户补全邮箱、兑换码、图片描述或金额后发送。转账继续走原有邮件确认流程。QQ 官方对 `enter=true` 的说明限于单聊，因此不依赖它实现群内直接执行。
- **接收与去重**：继续使用原有验签 Webhook，需额外接入 `INTERACTION_CREATE`。有效点击先写入持久化队列，再在 3 秒回调时限内调用 `PUT /interactions/{d.id}` 确认收到；确认请求本身限定在 2.5 秒处理预算内。结果使用本次点击的外层事件 ID 作为 `event_id` 被动回复，不复用帮助卡片的旧消息 ID。同一点击重复投递只执行一次；群被移出允许列表、机器人关闭或自定义指令停用后，排队中的按钮操作不会继续执行。
- **客户端兼容**：具体字号、边框和按钮展示由 QQ 客户端决定。菜单正文保留可手输的指令；若按钮点击无响应，先检查互动事件订阅、回应权限和后台任务，再用最新版手机 QQ 验收。帮助和翻页本身不调用 AI。

协议参考：[发送群聊消息与键盘字段](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_messages.post.html)、[互动事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/interaction_create.html)、[互动事件响应](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/interactions_interaction_id.put.html)。

### 群共享上下文

在「QQ 机器人 → 基础配置 → 免费 AI 聊天 → 群共享历史消息条数」设置最近历史消息数量，默认 **12 条**，范围 **0～100**；**0** 关闭并清空共享历史。数量包括群成员发言和实际发送成功的机器人聊天回复，每个 QQ AppID + 群分别保存，不读取或迁移旧版按成员保存的私有历史。旧配置 `history_turns` 按每轮 2 条转换，原来设为 0 的配置仍保持关闭；新配置使用 `history_messages`。

需接入 `GROUP_MESSAGE_CREATE` 并在 QQ 开启“接收所有消息”，才能看到未 @ 的群聊。未开启自主回复时，普通聊天只缓存，不创建模型任务、不占聊天次数；默认只有 @ 或回复机器人时才调用模型；开启自主回复的指定群按下述规则处理。发送给模型的每条群成员消息带群内稳定成员标识、可用昵称及消息/引用标识，昵称作为聊天数据处理，不作为权限依据。原有自定义人设保持不变。

历史部分使用本地 o200k tokenizer 估算，最多约 **1,500 Tokens**，单条历史最多约 600 Tokens；超长内容截断并优先保留最近消息，因此实际条数可能少于配置。这个上限不含人设、当前提问、明确引用原文及本次图片，不等于整次请求的计费上限；实际 Tokens 取决于聊天模型。没有摘要模型调用。连续 **30 分钟**没有可共享聊天后自动结束旧上下文，下一条消息开始新上下文；持续活跃时仅保留有界最近消息。

群成员消息使用 JSON 标注发言者及引用关系；机器人历史回复传给模型时只保留正文，避免模型模仿内部 `speaker/id/reply_to/text` 包装。普通聊天若仍返回完整的机器人历史包装（含内部消息标识，可带 JSON 代码围栏），在保存、分段及发送前提取 `text`，使任务结果、引用和后续历史均使用实际回复正文。普通 JSON 示例和正文中的代码不做通用字段提取，自主接话的 `action/text` 协议仍由独立校验处理；无需额外模型调用。

所有 `/` 指令、自定义指令、指令结果以及引用账户指令结果产生的追问和回答都不进入共享历史。明确引用仍只向当次请求提供原消息；引用优先于一般群历史。历史仅保留图片提示，不保存图片字节和临时下载地址。双事件投递使用同一消息 ID 去重，同群任务串行、不同群可并行，避免多人同时提问时互相覆盖历史。

### 群聊自主回复

后台入口：「QQ 机器人 → 基础配置 → 群聊自主回复」。默认关闭，启用时必须明确填写至少一个允许群的 OpenID，留空不会自动作用于所有群。仍需 QQ 全量群消息接收权限。配置不包含定时主动发言：所有回复都由收到的新消息触发。

- **直接呼叫昵称**：例如 `CTAV，帮我看看这个问题` 或 `CTAV你能帮忙吗`。必须出现在开头且构成称呼，正文提到名称不触发。走正常聊天、个人/全站额度和现有回复样式；不受自主活跃时段和自主调用限额限制。首版仅接收通过基础过滤的纯文本呼叫。
- **择机接话**：问句/求助优先成为候选；其他有效闲聊按配置抽样，偏好话题提供给模型参考。过滤机器人、指令、提及他人、引用他人、低信息短句、连续重复文本、链接、部分广告/凭据类内容及非纯文本。筛选后一次模型请求同时决定「跳过」或生成回复，不再二次生成。规则过滤只是保守筛选，不保证识别全部广告、敏感内容或人际对话意图。
- **一次续聊**：同一成员在机器人成功聊天回复后的 60 秒内发送可识别的追问，最多自动续接一次。需开启共享历史；跳过或失败也消耗本次续聊机会。续聊可越过群/成员间隔和消息数门槛，仍受时段、每小时/每日发送额度及调用额度限制。明确 @、引用机器人或呼叫名字继续走正常聊天。
- **短回复**：默认不额外 @ 发言人，每次仅发送一条约 100 字以内的文本，不自动生成图片。不输出处理中、额度不足或模型错误提示；后台保留原因。默认人设要求允许沉默、避免重复回答，不编造渠道/网站实时状态。

| --- | --- |
| 普通闲聊候选抽样 | 15%，设为 0 只保留问句/续聊等明确候选 |
| 群插话冷却 | 120 秒 |
| 普通插话前有效成员消息 | 6 条；自最近一次机器人成功发言起计算 |
| 同一成员自动回应间隔 | 600 秒 |
| 每群滚动一小时 / 北京日发送上限 | 3 / 20 条 |
| 每群北京日模型调用上限 | 40 次 |
| 活跃时段 | 北京时间 09:00～23:00，左闭右开；支持跨午夜，两端相同表示全天 |
| 同一成员续聊窗口 | 60 秒，0 关闭 |
| 回复长度 | 100 字 |

自主调用不占群成员个人聊天次数，但计入全站聊天调用额度，使用站长现有聊天连接。模型选择跳过、返回无效格式、失败或超时也占用已预留调用次数；发送失败或结果未知保留发送配额和冷却，不自动重发。任何自主调用/发送上限为 0 均关闭相应自主能力。独立调用次数只控制调用数量，不等于金额预算；金额上限继续由机器人专用 API Key 控制。

同群最多一个自主候选待处理，普通指令和明确聊天优先出队。自主模型请求最多等待 25 秒，消息入队超过 45 秒、生成期间群内出现新消息、配置关闭/群移除/时段结束或额度不再满足时，静默放弃。发送前再次核对长度与权限；网络请求已经发出后无法撤回。自主发送最多等待 15 秒。修改自主策略会取消尚未执行的相关任务，重启或开关切换不重置额度。

迁移 `285_qq_bot_autonomous.sql` 保存按 AppID + 群隔离的去重、计数和决策元数据，不额外保存群消息正文；既有任务/共享历史保留策略继续适用。去重记录保留约一天，筛选汇总约 32 天，任务约 30 天。后台显示北京日筛选原因汇总、实际预留模型次数、成功发送次数，以及最近 50 条机器人任务内的自主任务触发/跳过原因和 Token 统计。部署后建议先指定一个测试群，验证接收权限、引用和不额外 @ 的 QQ 客户端展示，再调整活跃程度。

### 图片理解与引用回复

发送 `@CTAV 根据这张图片说明问题` 并附上图片，或只 @ 并附图，机器人会将文字和图片一起发送给后台配置的聊天模型。需要模型和中转渠道实际支持图片输入；兼容 Chat Completions 的 `text/image_url` 和 Responses 的 `input_text/input_image` 格式。图片理解按聊天次数计数，不需要打开生图开关；`/生图`、`/画图` 仍是原有的文字生图，不是图片编辑。

支持 JPEG、PNG、GIF、WebP，每条消息最多 4 张，单张最多 10 MB、总计最多 20 MB，单张不超过 4000 万像素。图片通过独立下载器获取，只允许公网 HTTPS，禁止重定向及内网访问，不携带站长 API Key 或 QQ 凭据；验证图片内容后转成 Base64 发送给模型。读取失败、图片过大或格式不支持会直接提示，不会丢弃图片后只调用文字模型。

用户引用机器人回复并发送追问时，使用 QQ 回调 `message_scene.ext` 中的 `ref_msg_idx` 匹配发送成功响应 `ext_info.ref_idx`，将对应的那条已发送正文明确标记为引用内容。机器人自身回复也会在 QQ 提供源消息索引时携带 `message_reference`，在客户端展示引用关系。开启「接收所有消息」后，引用本机器人的已记录消息可无需再 @；引用其他人的消息或其他群的索引不会触发普通聊天。仍不能通过 @ 其他成员来触发机器人。

引用记录由迁移 `275_qq_bot_message_references.sql` 建立，按 AppID 和群隔离、保留 24 小时，只保存实际发送的正文、消息 ID、引用索引和图片标记。迁移 `278_qq_bot_group_history.sql` 新建共享消息表，并为引用添加能否进入共享历史的标记，旧引用默认不共享。引用始终指向具体原消息，不会替换成最近一条回答；同群普通聊天历史独立按配置加载。图片字节和临时下载地址不写入会话或引用记录，旧图细节需要重新附图。QQ 回调附带的引用、并行或合并消息中的文本和图片也会作为用户内容传入模型，递归深度及元素数量受限。

升级前的回复、过期记录，以及 QQ 没有返回索引和引用内容的消息无法恢复原文；@ 机器人追问时会说明未取得引用内容，不会猜测。引用机器人图片时，只有本次 QQ 回调重新附带图片才能读取图中细节。实际图片和引用展示需部署后在测试群验收。协议依据：[QQ 群 @ 消息](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_at_message_create.html)、[QQ 发送群聊消息](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_messages.post.html)、[OpenAI 图片输入](https://developers.openai.com/api/docs/guides/images-vision)。

### 奖励兑换

入口：「QQ 机器人 → 活动配置 → 奖励兑换」（`/admin/qqbot/activities?tab=redemption`）。管理员设置批次名称、奖励类型、生成数量、有效期和可选的网站领取用户 ID，每批可生成 1～200 个单次兑换码。额度为每码 0.01～1000 USD，最多两位小数；抽奖次数及奖品件数为每码 1～1000 的整数。实体和其他奖品可填写名称及公开领取说明；留空时提示联系管理员领取。有效期输入使用管理员设备时区，留空表示不过期。

用户先完成绑定，再在允许群内发送 `/奖励兑换 兑换码`。支持直接发送及 @ 机器人；直接发送需要 QQ 的接收所有消息权限。额度自动存入绑定账号，并写入奖励流水及 `admin_balance` 账本，**不计入有效充值、不额外赠送充值抽奖次数**。`/我的奖励` 追加兑换额度统计。抽奖次数接入现有赠送次数账本，能通过 `/抽奖次数` 查询并用于 `/抽奖`；使用抽奖功能仍须管理员开启抽奖活动。实体和其他奖品兑换后显示「待发放」，管理员实际交付后在该记录点击「确认发放」并填写后台备注；这一步只登记交付完成，不会自动寄送或再次加款。

后台可按批次、码尾号、记录 ID、用户 ID、邮箱和状态查询；查看领取账号、QQ 身份、兑换与发放时间；停用未兑换码。历史奖品及金额不可修改。已发放记录不能再次发放。兑换码绑定生成时的机器人 AppID；更换 AppID 后旧码不能在新机器人兑换，历史记录仍可管理。

兑换码使用密码学安全随机源生成 160 位随机值，支持忽略字母大小写及短横线。完整码仅在生成成功响应中返回，后台支持复制或下载 TXT；数据库只存 SHA-256 哈希与 6 位尾号，无法恢复原码。生成成功后请及时保存，丢失时应停用旧码重新生成。管理员接口禁用缓存，管理操作进入审计日志。QQ 回调在任务落库前移除兑换码原文及其他内容副本，只保存哈希；指令和结果不进入共享聊天历史，也不会交给模型。

防猜码固定启用：QQ 身份和网站账号共同限制，每次实际尝试至少间隔 **5 秒**；滚动 **15 分钟失败 5 次锁定 30 分钟**；北京时间每日最多失败 **20 次**。限制持久化于数据库，跨群、重启、多进程、重新绑定均不能清除原身份或原账号的限制。未知、错误格式、过期、停用、已兑换、非指定领取人、跨 AppID 码都统一返回「兑换码无效或不可用，请核对后重试」，不泄露码是否存在。未绑定用户不能查询兑换码。限流拦截不进入码查询，成功兑换也占用 5 秒间隔，不清零此前的失败次数。

领取、发放额度或次数、写入账本在同一数据库事务内完成。并发领取只有一个能成功；同一 QQ 消息重投使用原结果，不重复发奖。系统故障会回滚整笔事务；若发奖成功后 QQ 回复投递失败，奖励仍已到账，管理员可从兑换记录核对，重复发送同一码不会再次到账。

QQ群消息对群成员公开；贵重或定向奖品建议指定领取账号，以防完整码发出后被其他成员抢兑。收货信息应通过私下渠道交给管理员，不在群内索取或展示。数据库迁移为 `280_qq_bot_reward_redemption.sql`，抽奖赠送账本依赖 `279_gpt_direct_lottery_rewards.sql`。

### 自定义指令

入口：「QQ 机器人 → 基础配置 → 自定义指令」。点击「添加指令」，填写 `/a` 和对应回复内容，保持该条启用并点击页面底部「保存」。例如回复填写 `欢迎加入！\n使用教程：https://example.com`（在输入框中直接换行），群成员发送 `/a` 时便会收到这段固定文本。

最多 20 条，每条可单独启用、停用或删除；回复支持 Markdown 标题、加粗、列表和多行，金额建议使用 `USD` 避免美元符号与公式冲突，最多 2000 字，较长内容沿用 QQ 回复分段。名称以 `/` 开头，后接 1～32 个中文、字母、数字、下划线或短横线；省略开头的 `/` 保存时会自动补齐。重复名称和内置指令（含别名，例如 `/help`、`/画图`）会拒绝保存，停用条目也遵循同样校验。

按完整指令匹配，区分大小写，忽略前后空白；`/a` 不匹配 `/abc` 或 `/a 参数`。启用的指令自动追加到 `/帮助`，仅在机器人已启用且群在允许列表时生效，无需绑定账号、不调用模型或消耗 AI 次数。支持直接发送及 @ 机器人触发；直接发送需要 QQ 的「接收所有消息」权限，提及其他成员或其他机器人时不会触发。关闭某条后，未 @ 的该指令会被忽略，@ 机器人发送时返回未知指令提示。无需新增数据库迁移。

### 渠道状态

`/渠道状态` 无需 @ 或绑定账号，不调用模型、不消耗聊天额度。以 Markdown 文本先显示整体汇总，再列出各分组的成功率、错误率、缓存率和首 Token P50；默认统计最近 90 分钟，数据更新时间使用北京时间。帮助列表同步收录该指令。

复用 V2 被动监控的同一统计窗口、监控平台/分组配置、忽略错误分类和聚合结果；成功率与网页相同，为 `1 - 错误率`，整体指标来自原始汇总，不平均各组比率或延迟。整体和明细统一统计后台监控配置中的所有活跃分组，包含配置中的专属及订阅分组，不随发起人的个人绑定变化；监控分组列表留空时按全部活跃分组统计。混合平台分组沿用网页的平台/分组维度，并在同名分组后标注平台。

吞吐量跟随网站隐藏开关：允许公开时，整体和每个分组追加每分钟请求数和每秒 Token（TPM ÷ 60）。无请求显示「暂无请求数据」；无缓存统计或首 Token 样本显示「暂无数据」，真实零缓存仍显示 `0.00%`。历史回填或覆盖不完整会显示提示；监控关闭、当前为 V1 或查询失败时只返回简短提示。

成功率与错误率仅在请求量达到后台配置的最小样本数时展示百分比（默认 50，可配置）。有请求但样本不足时，两项显示「样本不足」，不将少数失败请求展示为确定的 `0% / 100%`；完全没有请求仍显示「暂无请求数据」。达到阈值且全部失败时仍展示真实的 `0% / 100%`。网页的整体、模型及分组矩阵同步以 `-` 表示样本不足，分组悬停说明原因。该规则只影响展示，不修改原始统计和聚合。

长回复按完整分组拆分，每次最多发送 5 条；超过时提供 `/渠道状态 2` 等翻页入口，每页重新查询当前数据，不截断分组明细。

## 邮箱绑定配置与流程

复用网站现有 SMTP 配置。在「系统设置」中配置可用的发件服务器，并填写「前端 URL」（`frontend_url`，也可使用服务器的 `server.frontend_url`）。生产环境填写用户能访问的 HTTPS 站点地址，用于生成邮件确认链接，不能填写模型 API 地址。

1. 用户在允许的 QQ 群发送 `/绑定 自己已注册的邮箱`。
2. 机器人先检查当前 QQ 是否已绑定；已绑定时仅回复“当前 QQ 已绑定账号。”，不再发送邮件或受理绑定码。邮箱对应账号已被其他 QQ 绑定时，仅回复“该邮箱已绑定其他 QQ，请联系管理员解除绑定。”，不发送邮件或生成确认链接。通过检查后先在群内回复“绑定申请已受理，请查收邮件并在 10 分钟内确认。”，再向该网站账号保存的邮箱发送确认邮件；不会等 SMTP 完成才回复。
3. 用户打开邮件中的链接，核对 QQ 昵称、成员 OpenID 和群 OpenID，点击「确认绑定此 QQ 身份」。不需要先登录网站；只打开页面不会完成绑定。
4. 绑定完成后可回群签到、查询额度；符合条件的邀请奖励会尝试自动结算。

邮箱必须对应有效且尚可绑定的网站账号，不会自动注册用户，也不会覆盖已有绑定。已绑定账号会提示绑定冲突，但不公开原绑定者身份；未知邮箱、不可用账号和未绑定账号仍使用统一受理提示。邮件确认链接有效期 10 分钟、仅可使用一次；重新成功请求后同一 QQ 身份的旧链接失效。网站邮箱发生变更、账号停用或删除、群移出允许列表、机器人关闭时，确认也会被拒绝。

发送限制按北京时间计算：每个 QQ 身份每天最多 5 次请求，每个收件邮箱每天最多 3 次，全站每天最多 200 次请求；同一身份和收件邮箱至少间隔 60 秒。失败尝试也占次数。SMTP 发送失败不会自动重试，后台日志会提示检查 SMTP 设置；用户仍可使用网站绑定码。

确认链接只存储令牌哈希，令牌放在 URL 片段中，确认页读取后清除地址栏片段，不保存到浏览器存储。刷新页面后需要从邮件重新打开完整链接。邮件或链接不可转发；非本人发起的请求直接忽略。

## 管理员查看与解除绑定

入口：「管理后台 → QQ 机器人 → 账号绑定管理」。支持按邮箱、网站用户 ID、QQ 昵称、成员或群 OpenID 搜索，每页 20 条；可查看网站账号状态、QQ 身份、来源群和绑定时间。机器人关闭时仍可管理已有绑定。

点击某行「解除绑定」，核对弹窗中的网站账号和 QQ 身份后，点击「确认解除绑定」。成功后相关网站绑定码和邮件确认链接一并作废，用户需重新发起验证才能再次绑定。旧页面或重复请求不会删除后来重新建立的绑定。

解绑不扣回已发放额度，不删除奖励流水或邀请记录。每天签到同时限制网站账号和 QQ 身份；邀请奖励也同时检查被邀请网站账号和 QQ 身份，避免换绑后重复领取。管理员操作与查看绑定列表会记录审计日志，普通用户无权访问这些管理接口。

## 随机签到配置

入口：「QQ 机器人 → 活动配置 → 签到配置」（`/admin/qqbot/activities?tab=checkin`）。旧地址 `/admin/qqbot/checkin` 自动跳转至此。设置开关、最低金额和最高金额，单位 USD，范围 0～1000，最多 8 位小数。例如 0.05～0.50，每次成功签到在这个区间等概率随机，包含两端；两个金额相等即固定奖励。可额外设置累计有效充值和近 N 天有效充值最低金额，单位 USD、最多两位小数；0 表示不启用对应门槛，两项都启用时满足任意一项即可签到。

有效充值按已完成的在线余额充值本金（扣除赠送和当前退款影响）及成功兑换的正额余额兑换码计算，不包含套餐、后台加款和签到/邀请/抽奖奖励。签到和邀请奖励可分别设置近期充值统计天数 N，范围 1～3650，默认 30 天；使用滚动 N×24 小时窗口。升级后旧配置仍按 30 天统计，无需数据库迁移。未达到条件时机器人直接提示当前累计/近 N 天金额和参与门槛；拒绝的签到不会占用当天资格，用户达标后可再次签到。

抽到 0 仍消耗当天签到资格。网站账号和 QQ 身份都受每日一次限制，解除绑定不重置资格。升级会继续使用原固定签到金额，直至管理员保存新的签到配置；基础配置页的保存不会覆盖独立签到设置。

## 抽奖活动与充值次数

入口：「QQ 机器人 → 活动配置 → 抽奖活动」（`/admin/qqbot/activities?tab=lottery`）。旧地址 `/admin/qqbot/lottery` 自动跳转至此。默认关闭；填写活动名称、每累计充值多少 USD、每档赠送几次，以及各奖项的名称、额度和中奖概率。最多 20 个奖项，单次额度 0～1000 USD，概率最小 0.01%，合计必须等于 100%。设置金额为 0 的奖项即“谢谢参与”，同样消耗一次。

可开启「累计抽奖保底」，设置周期 N（1～1000000 的整数）和独立保底奖池。每个网站账号在累计第 N、2N、3N 次抽奖时改用保底奖池，当次仍只消耗 1 次机会、发放 1 个奖品；其余次数使用普通奖池。保底奖池可配置 1～20 个奖项，概率独立合计 100%，每项额度必须大于 0、最多 1000 USD，支持 8 位小数。一个奖项设为 100% 即固定保底奖励。

保底默认关闭，升级后不会自动改变现有开奖规则，无需数据库迁移。计数包含该网站账号的历史抽奖，普通中奖、跨群、换绑和关闭后重新开启均不会清零。修改周期后按累计次数重新计算，只对后续抽奖生效，不补发历史保底。例如累计已抽 18 次，周期改为 10 次后，再抽 2 次即触发保底。每次结果保存开奖时配置与保底标记，后续改规则不改变历史记录；重复消息复用原结果，不重复扣次数或发奖励，入账失败会回滚整次抽奖。

开启保底后，`/抽奖活动` 展示保底规则及奖池，`/抽奖次数` 和抽奖结果额外显示距离下次保底的次数；保底当次明确提示已触发。后台用户次数查询展示保底进度，活动记录标记保底抽奖。

历史充值自动纳入，无需补发操作。每次查询或抽奖时计算 `floor(有效累计充值 / 门槛) × 每档次数 - 已抽次数`，可用次数最低为 0。比如每累计充值 $10 送 1 次，历史累计 $35 得到 3 次，剩余 $5 继续累计；抽过 1 次后剩余 2 次，再充值 $5 可多获得 1 次。

累计口径为已完成入账的在线余额充值本金（订单到账 USD 减去赠送），加上成功兑换的正额余额兑换码额度（`type=balance`、`status=used` 且有使用时间），包括活动开启前和绑定前的历史记录。在线订单生成的兑换流水按兑换码关联排除，不重复累计；任何状态的在线订单均不能通过兑换流水绕过完成状态、赠送剔除或退款规则。未使用、禁用、负额或零额兑换码、套餐购买、后台加款、签到、邀请、抽奖奖励均不计入，避免奖励循环增发；不使用可能带有不同币种和手续费的支付原币金额。

退款申请或处理中，该订单暂停计入。退款失败后恢复；部分退款按原本金比例扣除，全额退款不计入。已用次数不回退；若退款导致次数不足，后续充值先覆盖不足部分。已发奖不自动追回。结算会锁住所依据的充值订单和余额兑换记录，避免与退款或记录变更并发时读取旧状态。

当前是一套持续活动规则。修改门槛或每档次数会重新计算全部历史充值的资格，已用次数永久保留。关闭后再开启、修改活动名称、解除后重新绑定不会重置同一网站账号的已抽次数。不会生成多个互相独立、重复享用历史充值的活动。

用户发送 `/抽奖` 后消耗 1 次，中奖额度立即入账，失败的入账会回滚次数、奖励和流水。重复投递同一条 QQ 消息只返回原结果。抽奖记录和消息去重标识长期保留，不随普通运行日志清理。管理员可按网站用户 ID 查询有效累计充值、累计资格、已用与剩余次数，也可到「活动记录 → 抽奖记录」按邮箱、ID、QQ OpenID 分页检索抽奖记录，包含未中奖的参与记录。

抽奖配置与签到配置独立保存。管理员配置变更、次数查询和抽奖记录读取纳入审计；普通网站用户不能访问这些管理接口。群内活动需先绑定有效网站账号，并启用机器人及当前群权限。

## 活动记录

入口：「QQ 机器人 → 活动记录」（`/admin/qqbot/records`），替代原运行记录菜单；旧 `/admin/qqbot/runtime` 页面地址自动跳转。分为签到记录、抽奖记录、邀请记录三个 Tab，按当前机器人 AppID 查询，支持搜索和分页，金额统一显示两位小数。活动配置与活动记录可按当前 Tab 相互跳转。

签到记录展示成功签到（含零元）的账号、QQ 身份、群、金额与时间；抽奖记录展示每次已完成抽奖的奖品、到账金额、抽奖后剩余次数与时间，包含“谢谢参与”。这两个列表按原参与账号展示，解绑或换绑不会改变历史到账归属；当前绑定标识只在 QQ 仍绑定同一原参与账号时显示已绑定。

邀请记录仅来自 QQ 邀请进群，不包含网站邀请注册。展示邀请人与被邀请人的 OpenID、可用昵称、当前绑定账号及账号可用状态、群、申请/入群/退群时间，以及奖励状态、金额和原到账账号。只有收到官方 `GROUP_JOIN_REQUEST` 的有效邀请人字段，才能建立关系；只收到普通入群事件无法判断谁邀请了谁，不会补造关系。收到带邀请人的申请、尚未收到入群事件时显示待入群；未收到任何相关事件的邀请无法展示，历史缺失事件也无法追溯。

入群状态与奖励状态分别显示。未发放时，根据已收到的事件、当前绑定和活动规则显示双方待绑定、单方待绑定、账号不可用、邀请时间不符合规则、已退群、今日上限、邀请人充值门槛未达标或待结算等状态。状态是当前条件判断，并非历史发送失败日志。已到账奖励保留原账号，即使后来解绑、换绑或退群也不改写；同一被邀请人已由其他群或邀请关系结算时，不将其重复显示为本记录到账。查询列表不会触发奖励结算。

活动记录接口仅管理员可访问，读取纳入审计，响应不缓存。基础配置仍保留群发现所需的运行状态接口；任务队列与去重机制照常运行。

## 邀请奖励边界

入口：「QQ 机器人 → 活动配置 → 邀请奖励」（`/admin/qqbot/activities?tab=invite`）。设置每位新用户的邀请额度（USD）、每位邀请人每日奖励人数上限，以及邀请人账号的累计有效充值/近 N 天有效充值门槛；金额或次数为 0 时不发放，门槛金额 0 表示不启用。两项充值门槛均开启时满足任意一项即可领奖。近期统计天数可独立设置为 1～3650，默认 30 天；指令和未达标提示会显示配置后的天数。配置沿用原值，无需重新填写；邀请奖励与基础配置分别保存，并发保存也不会互相覆盖。

机器人必须在目标群担任群管理员，并在 QQ 开放平台订阅群成员事件 `GROUP_MEMBER_EVENT`（`1<<24`），接收 `GROUP_JOIN_REQUEST`、`GROUP_MEMBER_ADD`、`GROUP_MEMBER_REMOVE`。普通群成员身份无法收到带邀请人信息的申请事件，即使用户通过群内“＋”邀请好友，也无法建立邀请关系。QQ 凭据测试成功或聊天能回复，不代表具备该权限。配置完成后，请用一位此前未入群的新用户重新测试；缺失的历史事件无法自动补回。

官方 `GROUP_JOIN_REQUEST` 中 `apply_source=invited`、`invited_by` 用于记录邀请关系；`GROUP_MEMBER_ADD` 只有成员身份和入群时间，用于确认实际成功入群，不能单独推断邀请人。只收到申请时不会发奖励，缺少正式入群记录也不会发放。机器人开始记录以前的历史邀请不会追溯。官方说明：[用户申请加群事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_join_request.html)、[群成员加入](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_member_add.html)。

管理员身份和事件订阅是接收申请事件的必要条件，不能保证每次群内“＋”操作都包含有效邀请关系。排查时先确认实际收到的事件类型、申请来源和处理原因，不能只根据操作入口判断。容器日志可筛选 `qqbot.membership`，`stage=enqueue/process` 分别表示入队、处理阶段，`job_id` 可关联任务。群和成员仅记录哈希摘要，不记录原始回调、聊天、邮箱或凭据。

- `not_an_invitation`：申请来源不是 `invited`；`apply_source` 显示 `self_apply`、`missing` 或 `other`。
- `missing_inviter`：来源是邀请，但缺少邀请人字段。
- `self_invitation`：邀请人与申请人相同。
- `existing_inviter_or_late_invitation`：已有首次邀请归属，或本次申请时间晚于首次入群，未写入新关系。
- `invitation_recorded`：邀请关系已写入；是否发奖仍取决于入群、绑定和活动规则。
- `bot_disabled`、`group_not_allowed`：机器人关闭或当前群未开放；`invalid_invitation_time`、`invalid_membership_time`：事件时间格式无效；`database_error`、`reward_settlement_failed`：关系存储或奖励结算失败。

成功完成的任务会清空 `payload`。因此历史任务中 `payload->>'invited_by'` 为空，不代表原始回调没有邀请人；`completed` 也可能表示申请被规则忽略。诊断日志随容器日志保存，更新前已经清空的事件无法从新日志恢复。

双方已绑定时，在成功入群后自动结算；尚未绑定时，在完成网站确认绑定后尝试结算。未结算成功可由邀请人或被邀请人使用「/我的奖励」指令重试。相同被邀请网站账号只奖励一次；邀请人每日奖励人数受后台上限限制。直接分享群二维码后主动申请入群，通常没有官方邀请人字段，本版不会猜测邀请关系或发放奖励。

邀请奖励同时按被邀请人的 QQ 身份（当前 AppID 内）和网站账号（全站）永久去重。已奖励的用户退群后由其他人重新邀请、跨群邀请、解除后换绑，都不会再发一份奖励；同群已记录的邀请人不会被后续邀请覆盖。账号和 QQ 身份的签到资格也同时保留。补结算每次最多处理 100 条符合当前条件的记录，未绑定、已奖励或无效的旧记录不会占满批次；超过一批可再次发送指令继续结算。

发送 `/邀请奖励` 或 `/邀请活动`，无需 @，查看单人奖励、今日邀请入群人数、今日已奖励人数、每日奖励人数上限、双方绑定条件及充值门槛。邀请充值门槛只检查邀请人的网站账号；未绑定时也会显示规则并提示绑定。充值资格会显示达标状态和当前金额，后续充值达标后再次触发 `/我的奖励` 可补结算。每日按北京时间统计：入群人数按官方有效邀请和首次成功入群记录计算，同一 QQ 跨群去重，包含尚未绑定的被邀请人；已奖励人数按账户当天实际入账记录跨群汇总，与发奖上限口径一致。延迟绑定结算可能使两个人数不同。金额或每日上限为 0 时回复活动未开启。

发送 `/我的邀请`，无需 @ 或绑定网站账号，按当前机器人 AppID 和发起指令的 QQ 身份查询全部已记录邀请，显示待进群、待绑定、已奖励、已退群四行人数。待进群表示已收到带邀请人的官方申请事件，但尚未收到成功入群事件；待绑定包含已入群且双方或任意一方尚未绑定的用户。待结算、达到上限或无效邀请等其他状态不归入这四项，详细状态可在后台邀请记录查看。每位被邀请 QQ 跨群只计一次，优先保留已奖励状态，其次为已有其他邀请奖励及可继续结算的在群记录。已奖励后再退群仍计为已奖励。仅统计收到官方邀请关系的用户，无法归属邀请人的群二维码/链接入群不会计入。查询不会触发发奖；需要补结算时使用 `/我的奖励`。

## 活动安全与运营边界

发奖、绑定确认和模型用量预留在事务中读取当前配置，并与配置保存互斥。关闭机器人、移除允许群或降低邀请额度、限额后，后续授权按新配置执行；已经完成用量预留并开始调用的模型请求仍可能完成，不强制取消在途请求。签到和用量的每日统计使用一致的北京时间日期，签到唯一键与入账记录使用同一结算时刻，避免等待锁跨午夜时记入不同日期。

邀请结算锁定所依据的成员状态；退群更新先完成时，不会依据旧的在群状态发奖。网站绑定码和邮箱链接确认都会锁定请求与账号，验证账号有效、群仍开放，并在锁等待结束后重新检查有效期。绑定确认请求体和成员身份长度有上限。

余额、奖励流水、签到资格或已用抽奖次数在同一事务内提交；并发和重复事件不应产生重复入账。在线订单生成的兑换码按码值全站排除，不能因为历史导入记录的账号归属不一致而变成独立抽奖充值。以上验证使用隔离测试数据库和模拟接口，不代表生产部署或 QQ 事件投递已完成检查。

仍需按运营目标控制以下风险：

- 多个 QQ 配合多个网站账号仍可分别参与；邮箱绑定和双身份去重无法识别同一个真人。对新号、批量账号的限制需要额外的资格规则。
- 当前成功入群并完成绑定即可结算，没有留群时长要求。领奖后退群不自动追回；如果需要留存奖励，应增加留群时长及到期结算规则。
- 退款会减少后续可用抽奖次数，但已经发放的奖品不自动追回。抽奖门槛降低会按全部历史有效充值重新计算资格；免费发放的正额余额兑换码也会按当前规则计入。
- 签到和抽奖没有全站金额预算；邀请只有每人每日人数上限。模型限制调用次数而非账单金额，应在机器人专用 API Key 上设置金额硬预算，并按活动规模设置奖励额度。
- 邀请关系和退群状态依赖官方事件。未收到或尚未处理的事件无法代表 QQ 群的实时状态，不能承诺完整识别全部退群行为。

## 图片、消息与数据保留

- QQ 群被动回复窗口为 5 分钟，每条输入最多回复 5 次。机器人不使用主动消息来绕过窗口。
- 聊天与生图不再预先回复“正在思考中”，生成完成后发送结果；生图完成时先 @ 发起人提示“图片已生成”，随后发送图片。长文本在次数限制内分段发送，过长的回答明确标记截断。
- 生成结果保留 24 小时，不提供群内任务结果查询指令。
- 图片会转换为 JPEG，较大图片缩放至最长边 2048，以适配 QQ 上传限制。
- 上游图片 URL 只允许公网 HTTPS 下载，不携带 API Key，禁止跟随重定向到其他地址。
- 群聊天历史按配置条数限制并在连续 30 分钟无聊天后清理；为排除当前提问保留一个额外存储位。旧个人历史仍按原规则在 24 小时后清理且不再用于聊天；任务元数据和去重记录保留 30 天；奖励账目持久保留。
- 最多同时处理 2 个任务，同群串行、不同群并行；排队过久的聊天任务过期后不会调用上游。
- 处理进程异常退出的任务不会自动重新生成，避免对同一任务重复收费。
