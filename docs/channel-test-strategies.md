# 渠道账号检测策略

一条策略选择一组或多组账号分组，再选择要执行的检测项目。检测项目与答案均可配置。新建策略推荐使用“全部自动检测通过”，已有高级配置保留。

## 排除指定账号

在编辑策略的“排除账号”中，按名称或 ID 搜索并勾选所选分组里的账号，保存后生效。排除范围仅属于当前策略：该账号不参与此策略的手动检测、定时检测、失败重试和质量自动处理；业务调度开关及其他策略不受影响。取消勾选后从下次检测起参与。

排除名单在账号改组、临时停用后仍保留，重新进入策略分组时继续生效。修改名单视为检测范围变更，会使旧轮次失效并按现有策略更新机制清理旧保护；已发出的请求可以保存历史结果，但不能再执行自动暂停、恢复或改组。其他策略的保护和手动停止调度仍有效。

需要数据库迁移 282。API 使用可选的 `excluded_account_ids` 数组；更新时省略保留原值，传空数组清空，ID 必须为正数，重复 ID 自动去重。

## 每轮执行

- 每轮开始时读取所选分组中已启用检测的账号：未删除、调度开关开启，且状态为正常或质量自动暂停。过滤排除名单后按账号 ID 去重，保存完整的“账号 × 检测项目”名单；未启用账号不会生成待执行记录。
- 本轮名单固定。账号被检测结果移到另一组不会重新入队；中途新加入的账号到下一轮再检测。
- 不同账号仍可并发执行，每个服务实例最多同时发出 10 个上游请求；同一账号逐项执行。各项目按选择顺序执行。
- 同一账号的自动条件明确未通过、模型信息无法确认或执行失败后，本轮后续项目不再请求上游，并记录为“检测跳过”。仅展示、待人工评审的项目不作为“全部通过”模式的短路条件；其他账号照常检测。组合规则中，只在后续项目已不可能使任何组合条件成立时才提前停止。
- 手动重试与其他策略中的同账号检测也会等待该账号当前检测完成，不会与其同时请求上游；其他账号仍可并行。
- 排队期间手动停止调度、删除账号或改为不允许检测的状态，会在实际执行前阻止调用。仅由质量条件暂停的账号可继续接受检测。
- 每轮清空上轮的人工判定和票数，按当前轮结果重新判断。分组在出现有效新结论前保持当前状态。
- 修改检测范围或判断条件会使旧轮次失效。排队中的检测和重试会重新检查轮次，旧轮次成功结果也不能再自动恢复账号。分组的显示顺序调整不改变当前判定。

定时规则 `0 * * * *` 表示每小时整点运行一次。一次运行未结束时，同一策略不会启动重叠运行。

渠道质量检测列表、渠道监控中的检测结果和用户侧历史入口按账号当前状态过滤。未启用账号的旧结果也不显示，重新启用后恢复展示；质量规则自动暂停且调度开关仍开启的账号继续展示并参与恢复检测。管理端策略历史保留原始记录以便排查，无执行账号的分组汇总不受此过滤影响。

## HTML/SVG 内容检测提示词

输出类型为 HTML 的检测使用专用系统提示词，要求模型在一次响应中直接返回完整、可独立展示的 HTML（可内联 SVG、样式和脚本），或按题目要求返回完整 SVG。提示词明确没有工作区、文件系统、终端或工具执行环境，禁止列目录、读写文件、执行命令、调用工具，以及仅返回计划、解释或“已创建文件”的说明。

专用提示词替换该次检测请求中的默认编码代理指令，检测项目原有题目、输出 token 上限和推理配置继续生效。策略的手动执行、定时执行、自动重试和单项手动重试均使用同一规则；数字、模型一致性、普通连通性测试及正常网关请求不因此改变。

此约束通过各协议的系统指令字段发送。模型若仍未返回可提取的 HTML/SVG，或上游报告输出截断，继续按现有规则记为失败；提示词不替代输出校验。

## 重试、复测间隔与用量

- 所有检测执行错误都自动重试最多 3 次（首次请求加重试共最多 4 次），包括网络故障、超时、服务端、鉴权、余额、限流、参数、输出截断或格式校验错误及未知错误。每次重试默认等待 1 秒，重新计算执行超时；`Retry-After` 仍记录在请求历史中，不阻止本轮重试。任务取消或预算、质量保护等准入条件导致的检测跳过会直接结束。请求成功后的答案错误、模型不一致等质量结论沿用原判定。明确不支持可选参数时允许一次兼容重发，并记录每次真实请求。
- 同一策略下，每个异常账号的自动复测最短等待依次为 5、15、30、60 分钟，之后保持 60 分钟；上游要求等待更久时遵循其时间。定时任务仍按原规则触发，等待中的账号跳过整条检测队列，不延长等待或增加异常次数。其他账号正常检测。
- 手动检测可绕过复测等待，但仍检查账号状态、轮次和质量保护。完整检测队列得到有效通过结论后清除连续异常次数；无数据、样本不足、任务取消、数据库异常及仅重试单项不会据此宣告账号全面恢复。修改模型、提示词或策略配置后按新配置检测。等待状态保存在数据库中，服务重启及历史结果清理不会清除它。
- 管理端检测结果与历史记录可展开查看请求次数、输入、输出、推理及缓存 token。失败请求、自动重试、兼容重发、手动重试均保留用量；上游未返回的维度显示“未知”，不按零计算，任一请求缺失该维度时总量也为未知。推理 token 已包含在输出 token 内，不重复相加。检测用量独立记录，不写入用户计费用量。

## 简化配置：自动检测全部通过，人工评审可否决

在质量自动化中选择“全部自动检测通过”，为各检测设置“自动条件”“人工否决”或“仅展示”。任一自动条件异常或人工不通过即暂停；全部自动条件通过、没有人工否决时启用调度，并可选调整分组。人工通过不能绕过自动条件，待评审不阻止启用，仅展示的结果不影响调度。

项目和判断标准都可调整。例如将模型一致性、糖果设为自动条件，将鹈鹕设为人工否决；以后加入新的检测，配置其参与方式即可，无须修改调度代码。策略后续新增项目默认仅展示。至少需要一项自动条件，每条策略最多选择 32 个检测项目；需要复杂关系时改用组合规则。

新一轮结果未齐时保持原调度状态；已有暂停必须等待本轮条件全部满足才解除。详细步骤见[全部自动检测通过](channel-quality-protection.md#全部自动检测通过推荐)。本模式不需要配置下面的优先级和组合规则。

## 高级配置：多项检测如何决定分组

选择“组合条件”模式时，可以直接配置“且 / 或”及嵌套条件，每条规则满足后同时执行分组和调度动作。具体设置与“两项都通过进 A，任一失败进 B”的示例见[组合条件与动作](channel-quality-protection.md#组合条件与动作)。已有策略默认保留下面的按检测项目处理逻辑。

每个检测项目可分别设置条件、处理优先级、通过动作和不通过动作。

1. **必须通过的自动条件**：未完成或未通过时，阻止其他规则的通过分组动作，包括管理员点击通过。明确失败时优先执行该条件的不通过分组动作；没有设置切组动作时，仍允许其他明确失败执行降级。
2. **管理员本轮判定**：高于普通自动结果和用户投票。同一轮后续的普通检测结果不能推翻管理员判定；下一轮清空。
3. **普通规则优先级**：数值越大越优先，范围为 0–1000。同一优先级的自动条件全部通过后才能执行通过动作；任一失败先执行失败动作。
4. **等待评议**：没有判定的评议项目不阻止其他规则处理；已有用户投票结论按配置优先级参与处理。

同层、同一判定的多个切组动作合并其目标组。若希望最终只属于一个组，让同层动作选择相同的单个目标组。高层已经作出明确的不切组决定时，会保持现有分组。

“指定分组”会直接替换账号的全部原分组。至少选择一个目标组，且目标组必须在策略检测范围内，确保下一轮仍能检测这个账号。

调度暂停/恢复单独按各项检测的保护状态处理。其他条件尚未解除的暂停，不会因一次切组而被解除。缓存率检测仍可配置冷却和小流量试用恢复。

## Pro 与 Pro-不降智配置示例

策略分组选择 `Pro-不降智`、`Pro`，定时规则设置为 `0 * * * *`。组名前后顺序就是这条策略下用户端的显示顺序。

| 检测 | 条件或评议 | 优先级 | 通过目标 | 不通过目标 |
| --- | --- | --- | --- | --- |
| 糖果 | 数字等于 21 | 0 | Pro-不降智 | Pro |
| 模型一致性 | 按响应元数据核对模型 | 0 | Pro-不降智 | Pro |
| 鹈鹕 | 开启人工评议，可独立开关用户投票入口 | 100 | Pro-不降智 | Pro |

只需要切组时，将各项动作的调度状态设置为“保持不变”。

糖果与模型一致性都通过后自动移入 Pro-不降智。任一自动条件失败则移入 Pro。鹈鹕尚未评议不会阻止自动分组；管理员点击鹈鹕不通过后移入 Pro，点击通过后移入 Pro-不降智。

如果模型一致性无论如何都必须通过，勾选它的“晋级前必须通过此自动条件”。此时模型一致性失败或未完成，管理员点击鹈鹕通过也不能晋级。

## 用户端与重复策略

### 手动移出策略分组

在账号管理中修改分组、移除分组或清空分组后，若账号已不属于某策略的任何检测分组，系统会在同一事务内清理该策略对该账号的规则保护和组合保护，并刷新调度缓存。仍属于该策略的其他分组时，保护继续生效；其他策略的有效保护、人工禁用和停止调度也会保留。

移出的账号同时撤销旧轮次的自动操作权限：正在执行的检测可以保存历史结果，但迟到结果不能再次暂停或改组，旧评审也不能恢复操作权限。重新加入后由新一轮检测接管。策略自身的自动切组仍沿用本轮检测结果。

网关遇到实时准入拒绝时，会释放已预留的并发槽位；生图请求返回 HTTP 503 和错误码 `gateway_account_unavailable`。真实的并发等待超时仍返回 HTTP 429。启用高级调度时，会继续尝试其他候选账号，不会把已拒绝的账号放回等待队列。

此行为需要数据库迁移 281。迁移仅添加轮次权限标记，不会批量解除已有保护；历史遗留账号可通过重新保存正确分组触发定向清理。

用户端仍按账号实际所属分组显示检测结果，并实时刷新分组归属。合成一条检测策略不意味着把两个用户分组合成一个；没有当前可见结果的分组不会显示。

同一个账号或分组不应由两条启用的切组策略同时管理。保存策略会检查冲突；执行时也会再次检查账号范围，避免账号后续增添分组导致重复检测和相互改组。

## 旧配置升级

迁移 265 将旧专用工作流转换成通用规则，保留已配置的答案、动作及投票门槛。旧的隐含暂停/恢复动作会转换为明确动作；历史结果与账号现有分组保留，旧轮次判定不再生效。

旧指定账号、分组汇总、需要扩展检测范围、失效分组或互相冲突的策略会停用，并在列表显示原因。打开编辑器确认分组、检测项目和动作后保存，再重新启用。新版运行逻辑不再读取旧的专用工作流配置。

新版创建策略使用 `group_ids` 和 `test_definition_ids` 数组，不再使用旧的单分组、单账号或检测类型别名作为执行模式。
