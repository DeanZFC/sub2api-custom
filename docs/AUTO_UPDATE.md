# 自动更新说明

网页发起更新并查询进度，Linux Docker + systemd 宿主更新器负责核验与部署。发布版本由 FORK_VERSION 和对应 release manifest 标识；源码推送本身不等于完成发布。

## 更新流程

1. 确认部署配置与当前应用镜像，记录可用于恢复的镜像 ID。
2. 读取目标版本 manifest，验证版本、源码 revision 及当前 CPU 架构的不可变镜像引用。
3. 拉取镜像，核对实际镜像 ID、版本标签和 revision，提取目标更新器程序。
4. 持久化目标镜像 ID 和部署检查点后，写入 Compose overlay 并重建应用容器。
5. 校验实际运行镜像与应用健康状态，原子替换更新器程序。
6. 将完成状态写入临时文件并 fsync，rename 后同步状态目录；持久化成功后报告成功、释放更新锁并触发进程重启。

## 状态写入失败与重启恢复

关键检查点写入失败会中止后续步骤并保留更新锁，任务显示状态持久化失败。完成状态写入失败时仅重试写盘，不重新部署；在当前更新期限内持续尝试，失败期间不报告成功，也不触发成功重启。修复状态目录权限或磁盘空间后，可重启更新器继续恢复。

启动时会检查未完成部署。如果持久化的目标镜像 ID 与正在运行的健康应用一致，则恢复安装目标更新器并补写成功状态，避免因最后一次状态写入失败而回滚健康版本。目标未通过核验、正在回滚或旧任务缺少可核验镜像 ID 时，按已有流程尝试恢复更新前镜像。恢复同样以状态成功落盘为完成条件。

PostgreSQL 和 Redis 数据卷保留。更新器不自动备份 PostgreSQL，也不回滚已执行的数据库迁移；管理员应按部署要求准备数据库备份。恢复旧镜像不能证明数据库兼容，需结合版本迁移要求判断。多实例升级应协调所有副本的版本与数据库迁移。

## 排查

检查实际部署的更新器 systemd 服务日志、状态目录可写性、磁盘空间，以及应用容器镜像 ID 和健康状态。状态文件保留在配置的 StateDir，权限为 0600；不要通过删除进行中任务状态绕过更新锁。
