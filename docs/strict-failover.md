# 严格主备账号调度

## 配置

管理后台 → 分组管理 → 编辑分组 → **严格主备**。

1. 先将账号绑定到分组。
2. 开启严格主备，在“第 1 优先级”选择主账号；在“第 2 优先级”选择备用账号。
3. 可以继续添加、上移或下移层级，保存后生效。最多 10 层、1000 个账号，账号不能重复，每层至少一个账号。

新分组默认关闭。创建分组后再绑定账号、编辑层级；复制分组会将严格主备重置为关闭，避免沿用原分组的账号引用。关闭开关会保留已填写的有效层级。

配置存储为 groups.strict_failover，例如：

    {"enabled":true,"tiers":[[11,12],[21,22]]}

此例先使用账号 11、12，只有它们都明确不能承接本次请求，才使用 21、22。未列入任何层级的账号不参与推理调度。普通账号优先级、评分、成本、订阅偏好和会话粘性仅在选定层级内生效。

## 可用性规则

每次选号先直接读取配置中的所有账号及分组成员关系，包括调度缓存通常会过滤掉的禁用、冷却账号。按层级顺序选取第一个还有可用账号的层级。

可作为不可用依据：

- 账号删除、移出分组、停用、关闭调度、到期自动暂停。
- 已生效的账号或模型限流、冷却、额度耗尽、主动测试保护。
- 当前平台、模型、端点或 WebSocket 传输能力不支持，隐私要求不满足；影子账号的母凭据不可用。
- 本次请求完成允许的同账号重试后，收到明确的上游 HTTP 401/402/403/429/500/502/503/504/529，或已分类的凭据、余额、流式限流/过载错误。明确标为请求级或服务商级的故障不作为账号不可用依据。

以下情况不会凭自身触发降级：本地并发满、排队、评分低、利润门不通过、探测预算耗尽、数据库读取失败、没有故障证据的候选排除、本地合成的超时/断流 502/504。若当前层仍有其他账号，先尝试同层；若只剩未知状态则返回错误，不能跳层。已有持久化冷却/保护状态仍遵循系统原有健康规则。

重试次数与全局账号切换预算继续有效。预算提前耗尽时请求结束，不会为了进入备用层无限重试。没有已记录不可用状态的上游问题需要实际请求提供证据；本功能不主动发送收费探测请求。

## 恢复、续接与兜底

- 账号状态恢复后，下一次重新选号会重新从第一层开始。已经发出的请求按原账号完成，排队请求沿用当次选号结果。
- 普通新请求不会因会话粘性长期滞留备用层。
- 不可迁移的 previous_response_id 必须保持原账号，即使同层另一个账号可用也不能替换凭据。原账号不在当前可用层时返回 strict_failover_owner_bound（HTTP 409），客户端需携带完整上下文新开请求。
- WebSocket 后续 turn 会复核当前层与连接账号；层级变化时要求带完整上下文重连，不在原连接内混用凭据。
- 所有配置层都明确不可用后，才允许 API Key 已配置的跨分组兜底；未知状态、预算、并发或一般选取失败不能触发它。备用分组自身仍执行其严格主备规则。
- 启用严格主备时，Claude Code 客户端限制、prompt-too-long 的历史跨组兜底不会绕过层级限制。
- 固定账号获取模型列表、管理员主动测试、已创建媒体任务的查询/下载不是新推理调度，不改写其原有账号归属。

## 诊断与升级

日志 strict_failover_tier_selected 记录 group_id、model、tier 和前层逐账号不可用原因；strict_failover_all_tiers_unavailable 表示所有配置层均已确认不可用。strict_failover_unconfirmed 表示证据不足，请求没有启用备用路由。

迁移 325_group_strict_failover.sql 添加 JSONB 列，默认关闭；认证缓存快照版本升级至 28，配置进入认证投影且切片独立复制。账号层级 ID 仅在管理员 DTO 暴露，不在普通用户分组 DTO 暴露。部署时须使用包含该迁移的新服务端与对应前端；本地实现和测试不代表已发布或已安装到生产环境。
